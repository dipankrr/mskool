Fourteen tables in four layers: **configuration** (`fee_heads`,
`fee_structures`, `fee_structure_lines`, `late_fee_rules`), **resolution**
(`student_fee_assignments`, `fee_concessions`,
`student_optional_fee_subscriptions`), **billing** (`fee_installments`,
`opening_balances`), and **collection/ledger** (`fee_payments`,
`payment_allocations`, `fee_refunds`, `financial_transactions`,

billing/ledger db, **F3** config contracts+services, **F4** the billing
engine, **F5** collection, **F6** routers, **F7** tests, **F8** docs. One
chunk per commit, one layer per commit.

## Goal

Phase 4 per the roadmap — the money domain, where the codebase's hardest
invariants live. Behind the same pipeline as every prior phase (db →
contracts → services → routers → tests), with three load-bearing rules the
reference makes explicit and this plan locks: the append-only ledger (hard
rule 3), the row-locked receipt sequence, and the billing/collection
decoupling.

## Hard context an implementer must know

**Hard rule 3 is the phase's spine.** `financial_transactions` is
append-only: never UPDATE, never DELETE — corrections are new offsetting
rows. The table has NO `updated_at` BY DESIGN. Enforcement is a HAND-WRITTEN
trigger in F2's migration (`BEFORE UPDATE OR DELETE → RAISE EXCEPTION`),
marked like 0001's EXCLUDEs and 0008's double-mark guard, and proven by
`db:verify` — an application-only rule protects nothing at 2am with psql
open.

**Money is `decimal(10,2)` in the DB and STRING in code** (hard rule 4).
Drizzle numeric columns read back as strings; the contracts keep them
strings; no float ever touches an amount. Every CHECK on money in the
reference (`amount > 0`, `annual_amount >= 0`) is drizzle-visible.

**Billing and collection are deliberately decoupled** (DOMAIN.md §5).
`fee_installments` is what is OWED; `fee_fee_payments` is what ARRIVED;
`payment_allocations` joins them many-to-many — one cheque covering three
months, or half of one month, is the normal case. `paid_amount` on the
installment is the sum of its allocations; `balance_amount` is GENERATED
(`net_amount - paid_amount`), like the summary's percentage — the database
computes it, no code path can drift.

**Snapshots everywhere history matters:**
- `student_fee_assignments` snapshots `base_annual_amount` /
  `net_annual_amount` at assignment — revising a structure in October must
  not alter invoices already raised (DOMAIN.md's opening example).
- `fee_installments` snapshot amounts at GENERATION time — a revision
  affects only future (not yet generated) installments.
- `fee_payments.late_fee_amount` is frozen at payment time — a later rule
  change cannot alter a past receipt.
- Late fee is computed LIVE for display, frozen when charged.

**The receipt sequence is a counter table, not a BIGSERIAL** — formatted
receipts (`RCP-2025-00042`, prefix + year + number), sequential, immutable,
never reused. The service takes `SELECT … FOR UPDATE` on the
`(school, year)` row inside the payment transaction; two concurrent
cashiers must not collide. The `uq_receipt` unique index is the backstop,
not the mechanism.

**Payment status is a lifecycle, not a boolean**: `pending → cleared →
bounced/reversed/cancelled`. A bounced cheque is a real accounting event —
it writes a `Cheque_Bounce_Charge` ledger row and re-opens the installments
its allocation covered. Refunds reference the original payment and write
their own ledger row; nothing is deleted (hard rule 2).

**The `system` context (ADR-009) lands as SCAFFOLDING, not a gateway.** v1
collections are counter-recorded (cash at the desk, UPI ref typed in); the
`Online_Portal` mode is reserved in the enum, and F5 implements the `kind:
'system'` auth context + signature verification seam so the gateway
integration (deferred, owner's call on timing) is additive — the ledger
write path it will use is exactly the one F5 builds and tests.

**Scope columns are per-table** (the S2.4 lesson): every table here carries
denormalised `organizationId` + `schoolId`; the installment/ledger tables
add `studentId` + `academicYearId`. Money reads are year-scoped reads —
`includeHistory` is a REQUIRED argument where the year edge applies.

**Concessions are `fee_waiver:*` in the permission vocabulary** (the
authz names the CONCEPT, not the reference's word). Late fee rules and
opening balances ride the `fee_structure` family (configuration); install-
ment/dues reads ride `student_fee_assignment:read` +
`fee_payment:read`. These mappings are policy — owner-reviewed at F6 like
Phase 2's matrix additions.

## Money-safety discipline (owner-mandated, 2026-09-02 — binds every chunk)

This is the most sensitive subsystem in the app. The failure modes are NOT
validation errors — they are concurrency races and state-machine holes, all
invisible to `tsc`. The defenses, in layers:

1. **The database is the last line of defense, not the app.** Ledger
   immutability trigger; money CHECKs at the column level; GENERATED columns
   for every derivable number (balances, totals) so no code path can store a
   wrong sum; unique constraints (receipt, allocation pair, installment
   triple) as backstops under every concurrency race.
2. **One transaction per money movement, with explicit row locks.**
   `recordPayment` locks the receipt-sequence row (`SELECT … FOR UPDATE`),
   then locks the installment rows it allocates against — **in deterministic
   id order** (deadlock prevention) — and re-checks each balance INSIDE the
   transaction. Two concurrent cashiers serialize; neither reads a stale
   balance.
3. **State machines are named operations.** Payment status moves only through
   `clearPayment` / `bouncePayment` / `reversePayment` / `cancelPayment`,
   each validating the current state and writing its ledger rows in the SAME
   transaction. No free-form status PATCH exists anywhere.
4. **Rounding is stated and tested, never implicit.** Installment splits: the
   LAST installment absorbs the remainder, and `sum(installments) === net
   annual` is asserted exactly. Percentage concessions round DOWN (the school
   never over-discounts). Per-day late fee rounds the final day-count amount
   once, not daily. Each rule lives in one service function with tests.
5. **Concurrency tests against real Postgres.** F7 fires parallel
   `recordPayment` calls (separate connections) at the same student and
   asserts: exactly N distinct receipts, balances exact, exactly N ledger
   row-sets. Single-threaded tests would leave every race in this phase
   undiscovered.
6. **The invariant checker ships as a test.** After every scenario: ledger
   credits − debits per student equals collected − refunded − waived;
   every installment balance equals `net − paid`; allocations sum to their
   payment's amount. Drift anywhere is a loud failure, not a silent audit
   finding years later.
7. **Idempotency keys on money mutations** (the fintech-skill review,
   2026-09-02). A double-click or a network retry on `recordPayment` is a
   DUPLICATE COLLECTION, not a second one: two receipts for one cheque.
   `fee_payments` carries a nullable `client_reference` — unique per school
   where present — and `recordPayment` returns the existing payment when
   called with a key it already served, instead of writing a second row.
   The gateway era makes this mandatory anyway (webhooks replay; the
   provider's order id becomes the key), which is why the column lands in
   `0011`, not later.

## Locked decisions

| Decision | Choice |
|---|---|
| Ledger immutability | Hand-written trigger (F2): `BEFORE UPDATE OR DELETE ON financial_transactions → RAISE EXCEPTION`; db:verify proves it bites. |
| Money | `decimal(10,2)` / string in code; never float (hard rule 4). |
| Receipt numbers | Counter table + `SELECT … FOR UPDATE` in the payment transaction; format `RCP-<year>-<n>`; `uq_receipt` is the backstop. |
| Installment generation | Service-computed from structure lines × `installment_frequency` × the year's terms; mid-session admissions generate from `fee_effective_from`; `joining_month_full_charge` honoured. Idempotent (fills missing), like the calendar generator. |
| Paying ahead | SUPPORTED within generated installments (owner mandate 2026-09-02): an allocation may target ANY installment with a balance — future-due or not. Paying November's fees in October is the normal Indian-school case, not a feature. The ONLY refusal is exceeding a balance; there is NO due-date check anywhere in F5. |
| Late fee | Computed live for display; frozen into the payment when charged. Per_Day accrual computed at charge time. |
| Refunds | Reference the original payment; write their own ledger rows; never delete the payment. |
| Bounced cheque | A ledger event (`Cheque_Bounce_Charge`); allocations stay, installment balances re-open. |
| Gateway / Online_Portal | DEFERRED — the `system` auth context + signature seam lands in F5; the gateway itself is additive later. |
| Status machine | `fee_payments`: pending → cleared → bounced/reversed/cancelled, transitions named operations (the enrollment pattern), `status_updated_by/at/reason` recorded. |
| Waivers | `payment_status = 'Waived'` is a management act (`fee_waiver:approve`), writes a `Waiver_Applied` ledger row. |
| GST/tax | Flags only (`is_taxable`, `tax_amount` captured on ledger rows); reporting deferred. |
| Security deposits | Reserved (`Refundable` category, ledger types) — not built. |
| Commit cadence | One chunk per commit; tests ride with the code they cover. |
