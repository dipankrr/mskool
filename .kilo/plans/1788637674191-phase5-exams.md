# mskool — Phase 5: exams & results (17 tables)

Seventeen tables in five layers: **policy config** (`subject_types`,
`grading_scales`, `grading_scale_bands`, `pass_criteria`), **exam blueprint**
(`exams`, `exam_subject_schedules`, `exam_components`), **entry**
(`exam_eligibility`, `student_component_results`,
`student_component_result_revisions`, `term_assessments`), **computed chain**
(`student_subject_results`, `student_term_results`, `student_final_results`),
and **publication** (`report_card_templates`, `published_report_cards`,
`exam_class_publication`). Slices: **D1** docs, **B1** db, **B2** contracts,
**B3** exams-maths + property tests, **B4** domain services, **B5** routers,
**B6** integration/smoke/seed, **B7** hardening, then UI slices **S1–S5**
(each begins with the frontend-product-ux skill and a screen spec). One chunk
per commit, one layer per commit.

Build model: **backbone first, then slices.** The complete, tested domain
core lands before any screen influences anything; per-surface view endpoints
are designed only when their screens are, so none is ever designed blind.

## Goal

Phase 5 per the roadmap — the academic-integrity domain, where the product's
"exact reproduction in 2032" promise lives. Behind the same pipeline as every
prior phase (db → contracts → services → trpc → web, types flow one way),
with four load-bearing rules this plan locks: post-publication marks are
corrected only through the revision ledger (hard rule 7); the student portal
reads `published_report_cards` only (hard rule 8); marks writes are
two-fact-gated (ADR-029 subject gate — this phase is its first consumer and
owes the deferred HTTP proof); the marks-≤-max and grading-scale-lock
triggers land as hand-written migration SQL (ADR-013).

## Design decisions locked (the design review, 2026-09 — binding)

These were argued and settled with the owner across a full design review.
The ADR (chunk D1) is their formal home; this section is the implementer's
digest. Where this digest and older docs conflict, this digest wins and the
ADR supersedes explicitly.

**Subject typing — board-neutral (owner's model).**
- `subject_types` is school-defined: `name` (unique per school),
  `countsTowardResult`, `isGradedOnly`, `assessmentMode`
  (`exam` | `term_grade`), `sequence` (widget order), `is_active`.
- `class_subject_mappings` carries `subject_type_id` + `isElective` +
  sequence. The two booleans live ON the type, not the mapping (supersedes
  ADR-031's storage location; its independence principle survives — two
  booleans, never a mode enum, any combo allowed including counted+graded
  for GPA-mode primary classes).
- The 4-value `subjects.category` enum and the coscholastic `area` enum DIE.
  Co-scholastic areas become term_grade subjects the school defines; CBSE
  preset seeds the standard ones (`subjectTypes.applyPreset`).
- Mapping-assignment guards: type's flag/mode fields lock once any
  referencing (class, year, subject) has assessment data (name/sequence
  stay editable); reassignment to a type with different `isGradedOnly` is
  the ADR-031 flip-guard, now flowing through the type; deactivate never
  delete.

**Exam blueprint.**
- `exams.counts_toward_term_result` boolean — mocks/practice run the full
  pipeline but are exempt from the term sum-to-100.
- `exam_subject_schedules.pass_marks` (subject-level, default = Σ component
  pass marks, overridable — the "≥50/100 total" school rule).
- Strict coverage validation: every counted subject of a class is scheduled
  in every counting exam of the term. Relax later (renormalize) only on
  real demand — strict-first is additive-safe.
- Lifecycle: Draft → Scheduled → Ongoing → Marks_Entry →
  Under_Verification → Published → Locked, as an explicit transition map
  with preconditions (enumerated in the ADR): →Under_Verification requires
  all cohort component rows ≥Entered; per-class publish requires freshness
  + readiness; exam →Published when its last class is published.
- Template/config edits (schedules, components, pass criteria) refused once
  assessment data exists for the exam.

**Scales & policy.**
- `grading_scales.is_default` (one per school); components may override
  (ICSE case). Bands are PERCENTAGES, contiguous 0–100, validated
  gap/overlap-free. `Percentile_Rank` mode rejected in v1.
- `pass_criteria` unchanged in shape (must-pass subjects, grace caps,
  compartment caps, min_attendance_pct default 75).

**Grade-only paths.**
- Exam-mode graded-only subjects get an implicit single "Overall" component;
  grade lands via `grade_obtained` (schema already allows marks-NULL).
- `term_grade` subjects skip exams entirely; assessed in
  `term_assessments` keyed (student, term, mapping) — the reshaped
  coscholastic table. Class teacher is the default entry role.
- All-gradedOnly counted subjects → **GPA branch**: term/final aggregate is
  the grade-point average; percentage suppressed; ranks order by GPA;
  pass/fail counting skipped (promotion near-automatic at that level).

**Annual policy.**
- `terms.result_mode` = the annual aggregation policy ONLY:
  `weighted` (Σ term% × term weightage, weights must sum to 100) |
  `last_term` (annual = last term's result verbatim). Every term ALWAYS
  gets its own standalone result regardless.

**Elective seam (designed in now, built later).**
- Compute resolves each student's subject set through a RESOLVER function.
  v1 resolver = "all counted exam-mode mappings of the class" (roster from
  `student_enrollments` — no `student_subject_enrollments` needed). When
  elective machinery lands (additive: `subject_groups` +
  `student_subject_enrollments`), the resolver swaps to the enrolled
  subset — no engine rewrite, no snapshot-format break (snapshots already
  freeze each student's subject list per compute).

**Publication.**
- Per-class `exam_class_publication` records (exam + class + who + when);
  `exam.publishAll` is a loop over classes. Exam flips final-Published when
  the last class publishes.
- Verification optional: publish requires every cohort component row ≥
  Entered (no Drafts); Entered rows tolerated with a visible warning.
  New `marks:verify` permission — defaults: class teacher / VP / principal;
  subject teacher excluded (no self-verify); schools adjust via roles; the
  verify UI is the review view of the entry grid (badges, unverified
  filter, verify-row/all) — not a separate subsystem.

**Corrections.**
- Revision windows: `exam_class_publication` state `published →
  revision_open → re_issued`. During a window: each edit writes its
  `student_component_result_revisions` row FIRST (hard rule 7) and updates
  the mark, but NO recompute/re-version; all cards stay on their version.
- Window close: ONE recompute of affected students → ranks recomputed once
  → every rank-affected card re-versioned (new `published_report_cards`
  row, `replaces_version` set) in one transaction.
- Single-mark quick edit = an invisible auto-window of size one: one
  approval dialog with live impact preview ("1 result changes, 1 rank
  moves → 2 cards re-issued"), computed synchronously (compute is cheap),
  applied atomically. Quick edit disabled while a window is open for that
  class.

**Attendance eligibility — advisory only.**
- `exam_eligibility` never blocks marks entry or publication. It surfaces
  once on the publish-readiness screen (below-bar list, one-click "allow
  all"), and every allow/override decision + reason is recorded. Recompute
  on exam state transitions + manually; missing row = computed on demand.

**Ratified compute rules.**
- Grace order: must-pass subjects first, then largest deficit; never
  overshoot the pass line; per-subject and total caps respected.
- Compartment/detained boundary evaluated AFTER grace.
- Decimal library throughout; round half-up ONLY at storage boundaries;
  percentage computed from stored (rounded) totals.
- Computed rows carry `computed_at`; publish/re-issue refuses stale compute
  (any component `updated_at` > subject `computed_at` → recompute required).
- Resolved pass-policy snapshotted (JSONB) onto term/final results.

**Portal & product philosophy.**
- Admin = efficient ERP; parent = narrative layer (type widgets, remarks,
  attendance ribbon, clean download; client-side print incl. "print class
  set" via page-break CSS; no PDF infra in v1; server-side PDF deferred).
- Rule 8 clarified for analytics: portal may derive from PUBLISHED data
  only, never unpublished marks. Comparison privacy: aggregates/bands/
  percentiles yes; other students' identities or exact marks never;
  school-level opt-in. Trends/comparisons/gamification = recorded
  fast-follow extensions, zero schema change needed now.

**Marks entry.**
- Autosave per cell (single-row upsert, optimistic `updatedAt` guard,
  response carries fresh status+updatedAt).

## Hard context an implementer must know

- **Hard rule 1** — every exam table carries denormalized
  `organizationId` + `schoolId`; every service read takes a required
  `DataScope`; `scopeWhere` throws on unexpressible levels.
- **Hard rule 2** — never hard-delete any result row; deactivate/status.
- **Hard rule 4 (cousin)** — marks are `decimal(6,2)`, never float; money
  rules untouched here.
- **Hard rule 7/8** — see Locked decisions; the portal router (student
  procedure, ownership via `student_portal_access`) reads
  `published_report_cards.is_current` ONLY.
- **ADR-029** — `marks:create/update/delete` are SUBJECT_GATED_WRITES;
  router must use `staffProcedure(permission, { subjectGate: true })`;
  `check:builders` fails otherwise; miss = generic NOT_FOUND.
- **ADR-016** — `marks:publish`, `marks:delete`, `report_card:publish`
  bypass the Redis auth cache (already configured — do not disturb).
- **ADR-013** — the two triggers are hand-written migration SQL appended
  after the drizzle part; `db:verify` asserts them.
- **ADR-031** — exam chain reads `class_subject_mappings`-derived flags
  (now via the type), snapshots them at compute, never reads
  schedule-level overrides (no such columns exist — do not add them).
- Migration numbers: fees ended at `0012`. Phase 5 lands as `0013+`
  (split: config / blueprint+entry / publication+chain). VERIFY actual
  numbers at generate time (fees had to correct this same assumption).

## Exam-safety discipline (binds every chunk — the fees ledger's money-
safety section, transposed)

- A component result is ground truth: no code path updates a Published row
  except through the revision service (ledger row first, always).
- Snapshot at compute AND at publish: scale, max/pass marks, type flags,
  pass policy. A compute that can't snapshot what it used is a bug.
- Publication is transactional: all class snapshot rows exist or none do.
- Ranks never computed implicitly; always explicit, always snapshotted.
- The portal has no other table to read — that IS the enforcement of
  rule 8; never add a portal path around it.
- Absence is not zero. Exemption is not absence. Partial entry is valid.

## Workflow protocol

- Branch: `feature/phase5-exams` (created, off main). **Never commit to
  main. Never push.**
- One chunk per commit, one layer per commit, messages per the ledger.
  A chunk MAY land as several commits as real seams appear (fees landed
  20+ commits from 9 chunks); commits are never COARSER than a chunk.
- **Commit messages are DETAILED (owner-mandated).** Every message =
  conventional-commit subject + a body covering: (a) what changed and why,
  in a few sentences; (b) which design decisions/invariants the chunk
  applies, citing the ADR/hard-rule numbers where they bind; (c) files
  grouped by layer; (d) the exact gates run and their results. The
  reviewer's guide entry carries the deeper walk.
- Every chunk ends with the Verify gates green — all of them, or the chunk
  isn't done. Hermetic gates every chunk; integration + e2e locally per
  the ci.yml protocol (CI runs hermetic only by design — keep it that way
  unless the owner asks).
- After each chunk: tick its boxes here and append the ledger line — this
  file is the recovery anchor if a run dies mid-slice.
