# mskool — Phase 4 UI: the fees slice

The full fees surface gets its screens: **configuration** (fee heads,
structures + lines + late-fee rules), **student fee profiles** (assignment,
concessions, optional subscriptions, opening balances), **dues**, the
**collection counter** (+ receipt), **payments** (+ the named status
transitions + refunds), and the **ledger**. Eleven chunks: **UI1**
plumbing (money lib, types, copy, nav, tabs), **UI2** heads, **UI3**
structures, **UI4** fee profile, **UI5** subscriptions, **UI6** dues,
**UI7** the counter + receipt, **UI8** payments + transitions + refunds,
**UI9** ledger + opening balances, **UI10** durable E2E, **UI11**
close-out. One chunk per commit, one concern per commit.

## Goal

The backend under this slice (20 commits on `feature/phase4-fees`) is
complete, security-hardened, and frozen under owner review. This plan
builds its frontend — and the frontend must earn the same trust: it is
the surface that **sends money payloads and shows results**, and a UI
that sends wrong-but-valid payloads, shows stale state as truth, or
double-submits would corrupt money paths the backend cannot save it
from. Three rules make it competent by construction rather than by care:

1. **Forms ARE the contracts.** Every dialog is RHF + zodResolver on the
   exact `@repo/contracts` schema the server validates — an invalid
   payload cannot be typed into a valid request. Money fields carry the
   wire regex `^\d+(\.\d{1,2})?$` because the schema carries it.
2. **The UI never computes what the server owns.** Totals are derived
   read-only sums of allocations (the wire has no `amount`); late fee is
   never calculated client-side (there is no preview endpoint — the form
   says so, the receipt shows the frozen `lateFeeAmount`); concession
   amounts are server-computed and toasted back; balances shown after
   every money mutation come from invalidate + refetch, never from local
   prediction. **No optimistic updates on money paths.**
3. **The state machine is encoded in the UI.** The payment lifecycle
   (pending → cleared → bounced/reversed/cancelled, with terminal
   states) and its preconditions are rendered as the actions that
   exist, in the states they exist — an illegal transition does not
   render, so the UI cannot even propose it. Approve-tier actions
   (`fee_payment:approve`, `fee_waiver:approve`) are hidden, never
   disabled, from roles that lack them.

## Hard context an implementer must know

**This is the app's first money UI.** No `Intl.NumberFormat`, ₹, or
currency code exists in `apps/web` today. `lib/money.ts` is born in UI1
and is the ONLY module allowed to touch money formatting: decimal-string
⇄ BigInt paise conversion, `formatMoney` (en-IN, `tabular-nums` in every
money column), add/compare/clamp — **no float is ever constructed**,
including in display math and in tests. The wire regex is the contract
schema's; using the schemas as the forms enforces it client-side for
free.

**The tRPC mount is `fees.*` (plural).** Router comment says `fee.*`;
the actual mount in `router.ts` is `fees: feesRouter`, so client calls
are `trpc.fees.head.list`, `trpc.fees.payment.record`, etc. Row types in
`lib/trpc/types.ts` via `RouterOutputs["fees"]["head"]["list"][number]`.

**Every fee mutation requires `schoolId`** (`schoolParent` envelope) —
the `writeScopeArgs()` + `canSubmit` + `copy.access.chooseBranchTitle`
pattern from `use-students.ts`, honoring its null case. Lists send
`scopeArgs()` (`{ organizationId }`).

**Money on the wire is decimal STRINGS** (`"12000.00"`); integers like
`applicableFromMonth` are plain JS numbers; timestamps are full ISO
strings; dates-only are `YYYY-MM-DD` (display DD/MM/YYYY via
`formatIsoDate` — never a `Date` object for calendar dates).

**The counter shape is dictated by the backend (S1 "the counter
wire"):**
- `recordPayment` input: `studentId`, `academicYearId`, `paymentDate`,
  `paymentMode` (`cash|upi|cheque|neft_rtgs|card|dd` — `online_portal`
  is webhook-only, NOT a counter option), `allocations` (≥1 ×
  `{installmentId, amount}`), optional `transactionReference`,
  `bankName`, `chequeDate`, `remarks`, and `clientReference` (the
  idempotency key — the UI generates `crypto.randomUUID()` per attempt,
  regenerated after success).
- `amount` is NOT an input — derived server-side from allocations. The
  UI's total is a read-only sum.
- `lateFeeAmount` is NOT an input — computed server-side at charge
  time; frozen on the payment. No preview endpoint exists.
- Cash enters `cleared` immediately; every other counter mode enters
  `pending` ("Awaiting confirmation" — the Payments tab is where
  confirmation happens).
- Allocation guards the UI mirrors client-side as caps (server remains
  authority): each allocation ≤ the installment's `balanceAmount`;
  waived/cancelled installments cannot be paid; all installments
  belong to the paying student and year; over-allocation refused with
  the server's wording, dialog held open.

**The payment state machine (UI8 renders exactly this):**

| current | available transitions | permission |
|---|---|---|
| `pending` | Clear, Cancel | `fee_payment:approve` |
| `cleared` | Bounce, Reverse, Refund | Bounce/Reverse `fee_payment:approve`; Refund `fee_refund:create` |
| `bounced`/`reversed`/`cancelled` | none — terminal, "records kept" | — |

Every transition requires a `reason` (1–255); refund takes
`refundAmount` (capped best-effort at payment.amount − Σ prior refunds —
server is authority, its error names the refundable), `refundDate`,
`refundMode`, optional `transactionReference`. Waive (per-installment,
never-paid only) is `fee_waiver:approve`.

**Role matrix that shapes every screen (defaults; orgs may edit):**
accountant = all fee create/read/update + `student:read` but NO approve
(so: runs the counter, never sees Clear/Bounce/Reverse/Refund/Waive
buttons); principal = read everything + ALL approves but no create;
class_teacher = `student_fee_assignment:read` + `fee_payment:read`
(Dues + Payments tabs, read-only); vice_principal = `fee_report:read`
(Ledger tab only). The nav shows Fees if the caller holds ANY tab
permission.

**Dues rows are installment-level, no student names joined.** The dues
screen groups client-side by `studentId` and cross-references names via
the existing student list query. `duesListSchema.sectionId` exists but is
NOT picked by the router — no section filter (recorded deferral).
Totals are client-side sums via `lib/money.ts`.

**Opening balances have NO payment path** (record + list only; payments
target installments) — displayed as informational rows in the fee
profile, labeled honestly.

**Concessions have no list endpoint** (visible via net amounts,
`concessionAmount` returned at create, and `concession_applied` ledger
rows) and **refunds have no list endpoint** (the ledger's `fee_refund`
rows are the read path). Late-fee rules are create+list only — no
update/deactivate endpoint; sunset via `effectiveTo`.

**UX conventions standing from the console/UI plans** (locked there,
binding here): hidden-not-disabled gating; dialogs close on success
only (`mutateAsync`); FormDialog owns `preventDefault`; dates ISO on the
wire / DD/MM/YYYY display; row types from `inferRouterOutputs`; lists
send `{organizationId}` only, creates name parents via
`writeScopeArgs()`, row mutations address the row's own node
(`{organizationId, schoolId, id}`); per-permission degradation (missing
secondary permission → "—" column, not a failed screen); client-side
states, server-side authority; pure `lib/` helpers get unit tests;
one chunk = one commit.

**Walk-tooling notes (proven 2026-09-02/03):** native date inputs need
JS-set values through CDP; agent-browser does not auto-scroll (a
below-fold submit button eats clicks — scroll before clicking); toasts
expire ~4s — verify mutations in the DATABASE, not the toast.

## UX quality discipline (owner-mandated 2026-09-04)

The owner flagged past UX as not good enough. Binding rules for this
slice, enforced at each chunk's walk:

1. **Density where it matters, air where it helps**: money columns
   right-aligned `tabular-nums`; status badges tinted pairs
   (light/dark, the `DAY_TYPE_STYLES` idiom) never solid fills; page
   chrome consistent with existing screens.
2. **The counter is the flagship screen**: one-screen flow
   student-search → dues → allocate → collect; keyboard-first
   (Enter submits, per-row amount inputs in a stable order); the
   derived total prominent; late fee honestly stated ("added by the
   server per the school's rules — shown on the receipt"); receipt
   printable.
3. **Empty states explain the prerequisite chain** (Dues empty →
   "assign a fee structure first" → link); error wording from
   `lib/errors.ts` only; every user-facing string in `copy.fees`.
4. **Mobile-aware** (Indian front desks run phones): DataTable's
   card mode below 768px is a designed summary, not transposed
   cells; dialogs are bottom sheets on mobile (FormDialog handles
   this); the counter fits a phone.
5. **Accessibility**: labels visible (never placeholder-only),
   errors near fields, 44px touch targets, focus preserved, contrast
   pairs from the theme tokens, `aria-sort` on sortable headers
   (already in DataTable).
6. **Skills as gates**: `ui-ux-pro-max` searched per screen-chunk
   for its domain (forms, tables/data, navigation) before building;
   `vercel-react-best-practices` consulted for component/data-
   fetching patterns; `frontend-design` for the area's visual
   direction; `shadcn` for composition. Queries recorded in the run
